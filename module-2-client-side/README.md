# Module 2 · Client-Side Scripting

**Estimated time:** ~45 min  ·  **Topics:** 4

Control form behaviour in the browser using Client Scripts and UI Policies, including the catalog-specific variants used in the Service Catalog.

## Learning objectives

By the end of this module, you will be able to:

- Create onLoad, onChange, onSubmit, and onCellEdit client scripts
- Use UI Policies to control field visibility, mandatory, and read-only states
- Apply catalog client scripts and catalog UI policies to catalog items
- Decide between a client script and a UI Policy for a given requirement

## Prerequisites

Modules 0–1. You should understand client-side execution and basic g_form usage.

## Module recap

{% hint style="success" %}
You can shape the form experience entirely client-side and know when a declarative UI Policy beats a scripted approach.
{% endhint %}

## Why this makes you AI-ready

{% hint style="info" %}
AI reaches for a client script by default — even when a no-code UI Policy is the correct, faster, upgrade-safe answer. It will also write onChange scripts that fire on every keystroke and slow the form to a crawl. This module teaches you to judge *script vs. declarative* and to spot the performance traps, so you can reject generated code that technically works but shouldn't ship.
{% endhint %}
